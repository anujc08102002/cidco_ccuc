# System notifications

Implemented 22 October 2026 for all authenticated roles.

Updated 23 October 2026: **My workspace → Notifications** offers separate bell-list retention (1 minute through 30 days, or no automatic removal) and desktop banner duration (5, 10, 30 or 60 seconds, or until clicked/dismissed). Defaults are one day in the bell and ten seconds for a desktop banner. Save the workspace to keep these account preferences.

Bell retention starts when an item first reaches the browser. Expired items disappear and leave the unread count; this does not resolve or remove the underlying case or staff request. Reading a notification clears its dot and reduces the bell's unread count without prematurely removing the item. The bell also offers **Mark all as read**. Read timestamps and first-receipt timestamps are retained per account in this browser and synchronize between its tabs. They survive reload and sign-out, but do not synchronize across devices. A changed case workflow, legal-hold state or overdue state produces a new alert identity.

Clicking a desktop notification marks its source bell items read. The worker retains these identities for the portal to pick up even if no page was open at click time. Timed banners no longer request sticky display. The worker schedules closure, an open portal tab also schedules closure, and focus closes overdue banners. Exact background timing remains subject to browser/OS policy: [idle service workers may be terminated](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope), so the application cannot guarantee an exact timeout while all portal tabs are closed.

Open the notification bell and choose **Enable system notifications**. Allow the browser's permission prompt. Setup applies to the current account on this browser/device; each user enables it on their own devices. The bell offers a sound checkbox, **Test on my device**, and **Turn off here**. Permission is requested only after the user's click. The application cannot grant notification permission or override Do Not Disturb on another user's computer.

After **Test on my device** succeeds, the setup message and expanded controls are hidden automatically. This completion flag is saved with the enabled browser binding, so reopening the bell or refreshing does not repeat the setup panel. Notifications remain enabled. Use the compact **Manage system notifications** link to reopen sound, test and turn-off controls. Failed tests leave the setup panel visible for retry; only **Turn off here** explicitly disables delivery.

New recipient-scoped account, case-attention, and supervisor continuity entries trigger Web Push to the registered browser. The notification-only service worker displays a system banner even when no page is active, including when the browser is minimized. Opening a notification focuses the application and opens its relevant page/case. The worker never caches authenticated pages or API responses. Existing bell entries are baselined at setup so enabling does not produce a burst of historical notifications.

If browser registration fails with an aborted registration or push-service error, setup enables local delivery instead. The panel identifies this mode and asks the user to keep the portal tab open. The tab checks the authenticated, uncached `/api/me/push/feed` every fifteen seconds and on focus, and passes new entries to the same notification worker. Minimized tabs can receive alerts, subject to browser timer throttling; closing the portal stops local delivery. This mode preserves account binding, sound controls, baseline suppression and deduplication without saving a failed push subscription. Other setup errors still appear as errors. Turn off and enable again to retry background push after the browser/provider problem is resolved.

With sound enabled, background notifications request the normal operating-system notification sound. An unlocked portal tab plays a firm two-note attention signal lasting under half a second, including while minimized when the browser permits audio. Two crisp notes provide a recognizable cue without a long sustain. Triangle-wave fundamentals and a restrained octave voice provide a more present midrange tone, with smooth attack/release envelopes to avoid clicks. The browser-based audio check renders the actual implementation to `output/audio/enforceflow-notification.wav`, checks signal level and clipping, and verifies that muting prevents playback. The worker selects one tab to prevent multiple page chimes. Sound can be muted for this account on this browser without disabling banners. Operating-system/browser settings can silence or suppress notifications. Custom audio cannot be guaranteed by a background service worker; [the notification API's sound behaviour](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification) is controlled by the platform.

## Deployment

Use HTTPS for the client website and API in deployment. Localhost is supported for local development. An HTTP LAN address does not satisfy browsers' secure-context requirement. Chrome, Edge, Firefox, and other supporting browsers use their own push services; the API server needs outbound HTTPS access to those providers. Delivery requires network availability and a browser/OS that permits background notifications. Fully quitting a browser, device sleep, power-saving restrictions, revoked permission, or Do Not Disturb can delay or suppress delivery. Push does not guarantee a notification on every device regardless of system policy. See [MDN's background push guidance](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation).

The server generates and persists its VAPID key pair in ignored file `server/.push-vapid.json`, or uses `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT` from server configuration. Keep the private key secret and back it up with server secrets. Multiple server instances must share the same keys. Changing keys requires browsers to re-enable their subscriptions. Do not expose the private file or server directory through web hosting. The built client includes `/notification-worker.js` at the origin root; deploy the app with that root scope.

The existing SQL Settings table stores subscriptions under an endpoint hash. No schema migration is needed. Only authenticated account endpoints register or remove subscriptions. Web Push endpoints are restricted to recognised browser push services to prevent arbitrary outbound requests. The API records the session's expiry, password fingerprint and designation when subscribing; it rechecks these against the current user before dispatch. Disabled/deleted accounts, password/role changes and expired sessions stop delivery. Foreground use renews an already-enabled account's session binding without a permission prompt. Standard sessions last twelve hours; sign in again when they expire.

On sign-out or session expiry, the client clears its device binding, closes its displayed notifications and unsubscribes. Server deletion uses the old binding and owner so a delayed sign-out cannot remove a newer account's subscription. Push messages and notification clicks also require the worker's current user and random binding to match; late messages from another account are discarded. Changing accounts on a shared browser disconnects the previous account; the new account must enable notifications for itself.

The server dispatches on application changes and checks every fifteen seconds for deadline and holiday-window transitions. It groups simultaneous new entries, tracks stable item IDs, and retries transient push-service failures. Expired endpoints are removed. The test implementation uses fake transports and an isolated worker, so automated verification does not send real browser pushes or display system alerts.

## Checks

`npm test` includes backend subscription validation, session/recipient isolation, baselining, deduplication, renewal, retry, rebinding, and revocation tests. The actual worker script runs against an isolated IndexedDB to verify background display, sound flags, notification clicks, duplicate suppression and stale-account rejection. `npm run test:experience` exercises permission-on-click, enable/test/mute/disable controls and availability for different roles with fake browser APIs. A real end-to-end provider/OS banner check is intentionally left to each user's explicit **Test on my device** action; no real user's browser is subscribed by the automated tests.
